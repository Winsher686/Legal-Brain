# 通用 RAG 引擎 → 企业法务知识库 改造方案

> 目标：把一套多格式文档导入 + 混合检索 + 知识图谱 + 智能问答的通用 RAG 引擎，
> 改造成**面向公司法务团队、聚焦法律法规 + 合同范本**的企业法务知识库。
>
> 结论先说：**架构 80% 可以复用，核心改造集中在「领域语义层」（提示词 + 知识图谱 schema + 实体识别），而不是代码框架。**

---

## 二、核心设计：法务知识图谱 Schema

这是整个改造的**灵魂**。原项目用 `item_name`（商品名）做知识隔离的锚点，法务场景里对应的是**「法规名称 / 合同类型」**。

### 2.1 实体类型（Entity Label）设计

```python
ALLOWED_ENTITY_LABELS: Set[str] = {
    # 法规体系
    "Law",            # 法律（如《劳动合同法》）
    "Regulation",     # 行政法规/部门规章（如《劳动合同法实施条例》）
    "JudicialInterpretation",  # 司法解释
    "Article",        # 法条/条款（如"劳动合同法第39条"）
    "Clause",         # 合同条款（如"保密条款""竞业限制条款"）

    # 法律要素
    "Subject",        # 主体（用人单位、劳动者、股东…）
    "Obligation",     # 义务（缴纳社保、支付加班费…）
    "Right",          # 权利（解除权、优先购买权…）
    "Condition",      # 适用条件/前提（"连续工作满10年"）
    "Liability",      # 责任（违约责任、赔偿责任…）
    "TimeLimit",      # 时效/期限（诉讼时效、试用期…）

    # 合同要素
    "ContractType",   # 合同类型（劳动合同、采购合同、NDA…）
    "Amount",         # 金额/标准（违约金数额、赔偿上限…）
    "Exception",      # 例外/免责情形
}
```

### 2.2 关系类型（Relation Type）设计

```python
ALLOWED_RELATION_TYPES: Set[str] = {
    # 法规层级
    "SUPERSEDES",      # 新法取代旧法
    "IMPLEMENTS",      # 下位法落实上位法
    "REFERENCES",      # 援引/参见

    # 条文结构
    "REGULATES",       # 法条规范某主体
    "GRANTS",          # 授予权利
    "IMPOSES",         # 施加义务
    "PROVIDES_EXCEPTION",  # 规定例外
    "DEFINES",         # 定义某概念

    # 合同条款
    "CONTAINS_CLAUSE", # 合同包含条款
    "APPLIES_TO",      # 条款适用于某主体
    "SETS_PENALTY",    # 设定违约责任
    "SETS_TIME_LIMIT", # 设定期限
    "TRIGGERS",        # 触发条件
}
DEFAULT_RELATION_TYPES = "RELATED_TO"  # 兜底保持不变
```

### 2.3 实体名长度调整

```python
# 原：MAX_ENTITY_NAME_LENGTH = 15
MAX_ENTITY_NAME_LENGTH = 40   # 法条名/法规名更长，如"劳动合同法第39条"
```

> ⚠️ 注意：这个常量在两个文件里都有，需同步改：
> - `knowledge/processor/import_process/nodes/kg_graph_node.py`
> - `knowledge/processor/query_process/nodes/kg_search_node.py`（`_ENTITY_NAME_MAX_LENGTH`）

## 三、"商品名" → "法规名/合同名" 语义迁移

原项目里 `item_name` 贯穿全流程（识别 → 嵌入 → Milvus 存储 → Neo4j 隔离 → 查询过滤）。法务场景下，它对应的是**「文档主题标识」**，例如：

| 原场景 | 法务场景 |
|--------|----------|
| `item_name = "优利德 UT890D+ 数字万用表"` | `item_name = "中华人民共和国劳动合同法"` |
| 用户问"这个表怎么测电压" | 用户问"劳动合同解除要赔多少" |

### 3.1 需要改的提示词

**`prompts/upload/import_prompt.py`** —— 两个提示词重写：

- `ITEM_NAME_SYSTEM_PROMPT` → 改为「识别法规名称 / 合同类型」：
  - 优先识别法律文件的**全称**（如《中华人民共和国劳动合同法》）
  - 合同文件识别**合同类型**（如"劳动合同""采购合同""保密协议"）
  - 降级策略：无法识别时用文件标题
- `ITEM_NAME_USER_PROMPT_TEMPLATE` → 措辞从「商品名称」改为「法规名称/合同类型」

**`prompts/query/query_prompt.py`** —— 五个提示词重写：

| 提示词 | 原语义 | 法务语义 |
|--------|--------|----------|
| `ITEM_NAME_EXTRACT_TEMPLATE` | 提取商品名 | 提取法规名/合同类型 |
| `USER_HYDE_PROMPT_TEMPLATE` | 模拟产品说明书 | 模拟法律条文/合同条款内容 |
| `ENTITY_EXTRACT_SYSTEM_PROMPT` | 抽取设备/部件/操作实体 | 抽取法条/条款/主体/义务实体 |
| `ANSWER_PROMPT` | 说明书问答 | 法务问答（引用条款号 + 出处 + 风险提示） |

### 3.2 需要改的变量名（可选但强烈建议）

`item_name` → `doc_subject`（文档主题），涉及的文件较多，建议用 IDE 全局重命名，但要注意 **Milvus 集合字段名和 Neo4j 节点属性名 `item_name` 是持久化的**，改动需要迁移数据或保持字段名不变。**建议：底层字段名 `item_name` 保持不变（避免数据迁移），只在提示词和注释层面用「法规/合同」语义。**

## 四、法务场景特有的增强点（原项目没有，需要新增）

这是法务知识库区别于通用 RAG 的**差异化价值**，建议按优先级分期实现：

### P0（必须，直接影响可用性）

1. **法条引用出处回填**
   - 答案里必须带「《XX法》第X条」，来源 chunk 的 `title` 字段要存法规名+条款号
   - 在 `document_split_node` 或 `answer_output_node` 增加出处拼接逻辑

2. **合同条款级检索**
   - 合同文档按「条款」切片，而非固定长度切片（`document_split_node` 增加按标题层级切分策略）

### P1（强烈建议）

3. **法规版本/时效管理**
   - 法条元数据增加 `effective_date` / `expired_flag`，查询时过滤已废止法规
   - Neo4j 用 `SUPERSEDES` 关系链表达"新法取代旧法"

4. **法务免责声明**
   - `answer_output_node` 输出末尾自动追加固定免责声明："本回答基于知识库检索结果生成，不构成正式法律意见，具体请以现行有效法律法规为准。"

5. **MCP 网络搜索升级**
   - 原 `mcp_search_node` 是通用网络搜索，法务场景应接入**权威法律数据库**（如国家法律法规数据库 flk.npc.gov.cn），保证法条现行有效性

### P2（长期演进）

6. **权限分级**：法务团队内部不同角色可见不同知识域
7. **合同比对**：上传合同 vs 范本的条款级 diff
8. **风险预警**：基于知识图谱识别合同中的高风险条款

## 六、风险与注意事项

1. **`.env` 里现在明文存着 API Key / 数据库密码**，作为企业项目务必改造成 `.env.example` + 环境变量注入，并加入 `.gitignore`（已确认 `.env` 目前未在忽略列表中需检查）。
2. **数据迁移**：如果底层字段名 `item_name` 要改，Milvus 集合和 Neo4j 属性都得重建；**建议保持字段名不变**，只在语义层做映射。
3. **法律准确性**：LLM 生成答案可能有法律错误，必须保留"出处引用"让法务人员可溯源核实，这是法务场景的**底线**。
4. **法规时效**：知识库里的法规会过期，需要设计更新机制（重新导入 + `SUPERSEDES` 关系标记）。
